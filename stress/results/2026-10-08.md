linux-64, osx-arm64 and win-64. Each failure below has a root cause, the
evidence, and what would fix it. No fix is applied. The ones that change
the toolchain are listed at the end for the user to decide.

## Root causes

### Z: zig 0.16 behaviour (rzig passes the flags through)

Each Z item reproduces with plain `zig cc`, conda-forge's and upstream's
zig alike. The reporter checked Z1 to Z3 and Z5 to Z8 and Z10 again on
gamma with both zigs (Z5, Z7 and Z8 by cross-compiling); Z4 and Z9 come
from the linux runner's repros.

- **Z1. `-Werror=date-time` at `-O1` and above.** zig adds it (`zig cc -O2
  -###`; not at `-O0`). Any `__DATE__` or `__TIME__` stops the compile.
  duckdb on all three OSes (`duckdb/third_party/pcg/pcg_extras.hpp:628:25:
  error: expansion of date or time macro is not reproducible
  [-Werror,-Wdate-time]`), arrow's bundled mimalloc 3.4.1 on linux and
  macOS (`src/options.c:236`). Fix: rzig adds `-Wno-error=date-time`.
  Tested as `CPPFLAGS += -Wno-error=date-time` in a site Makevars and as
  `add_compile_options` in a CMake toolchain file.
- **Z2. `-L` inside `-Wl,` is rejected.** `error: unsupported linker arg:
  -Ltbb/build/lib_release` (also `-Xlinker -L` and `--library-path`). GNU
  ld takes it. RcppParallel on all three OSes and its system-tbb variant
  on linux and macOS; behind RcppParallel: stringfish, qs2, StanHeaders,
  rstan. Fix: rzig moves it out as a plain `-L`. Tested with a
  `PKG_LIBS` that uses `-L`.
- **Z3. The linker option `--dependency-file` crashes zig** (linux only).
  conda-forge's zig panics (`thread N panic: index out of bounds: index 0,
  len 0`), upstream's segfaults. CMake 4.4 adds `-Xlinker
  --dependency-file=...` to every ELF link when the linker it identified
  lists the option in `--help`. Here it identified LLD 23.1.1, the
  `<env>/bin/ld.lld` of lld-zig, which flang-zig (universe) depends on.
  macOS and Windows are not ELF, so CMake never adds it there. Hit:
  RcppParallel's bundled TBB, Rhdf5lib's libaec, arrow:source's zlib. Fix:
  rzig drops the option in all its spellings (CMake builds and rebuilds
  without the file). Tested with `CMAKE_LINK_DEPENDS_USE_LINKER OFF` in a
  CMake toolchain file.
- **Z4. lld's `--no-undefined-version` default** (linux). TBB's tbbmalloc
  version script names symbols the link does not define: `version script
  assignment of local to symbol ITT_DoOneTimeInitialization failed: symbol
  not defined`. GNU ld accepts it. Only RcppParallel, behind Z3. Fix:
  `-Wl,--undefined-version` on linux links that have a version script.
- **Z5. `-march=armv8-a` is read as a CPU name** (aarch64). `error: unknown
  CPU: 'armv8'`, also with `+crc`. arrow's CMake pthread probes add it, so
  the R log shows only `Could NOT find Threads`; the real error is in
  `CMakeConfigureLog.yaml`. Then bundled aws-checksums fails on its own
  `-march=armv8-a+crc`. macOS here; linux-aarch64 has the same zig
  behaviour (repro on gamma). Fix: rzig rewrites it to `-mcpu=generic+v8a`
  plus the extensions. Not tested together with PR #14's `-mcpu=baseline`,
  which is now on main. Tested only by turning arrow's SIMD off
  (`ARROW_SIMD_LEVEL=NONE`, `ARROW_RUNTIME_SIMD_LEVEL=NONE`) and S3 and
  GCS off, which drops NEON kernels.
- **Z6. A link input without a known extension is rejected** (macOS V8).
  V8's autobrew script renames `libv8_monolith.a` to `.deps/v8_monolith`;
  zig says `unrecognized file extension`, ld64 reads the file. Fix: rzig
  could give such an input an `.a` name when it is an archive, or leave it
  to zig. Tested by linking the same bundle as `-lv8_monolith`.
- **Z7. `-c` without `-o` writes `<stem>.obj`** (Windows). MinGW gcc writes
  `<stem>.o`. QuickJSR then runs `ar -rs ... libquickjs.o` on a file that
  does not exist; this skips rstan. Fix: rzig adds `-o <stem>.o` for `-c`
  with one source and no `-o` (diff rzig-3, tested on kappa).
- **Z8. `-Wl,--allow-multiple-definition` is rejected** (Windows
  StanHeaders' Makevars.win). With an empty `PKG_LIBS` it links: there are
  no duplicate symbols. No diff yet.
- **Z9. Linux: no `__cxa_finalize` when a zig-built shared library is
  unloaded.** zig links linux-gnu shared libraries without crtbeginS.o:
  no `.fini_array`, and lld's `__dso_handle` is the image base. Static
  destructors registered with `__cxa_atexit` stay behind after `dlclose`,
  and glibc calls them at exit: R segfaults. Seen with `unloadNamespace()`
  for lme4 and fstcore (2 of 71 compiled packages; exit status 139), and
  after a compiled and sampled Stan model (the results are right: mu 3.10,
  Rhat 1; gdb shows `exit()` calling an unmapped address). R CMD check's
  "can be unloaded cleanly" check would fail the same way. A two-file
  repro (`lib.cpp`, `main.c`) crashes with a zig `.so` and not with a gcc
  `.so`. Candidate fix, tested in the repro: link a small object
  (`fini2.c`) into linux shared links that defines `__dso_handle` and a
  `.fini_array` entry calling `__cxa_finalize`, which is crtbeginS.o's job.
  macOS: no crash, because dyld never unloads an image with thread-local
  variables and zig's static libc++abi has one (`eh_globals`); the side
  effect is that a package reloaded in the same session keeps its old
  code. All 76 compiled packages unloaded and exited 0 there. Windows: no
  crash for the nine packages tried.
- **Z10. Debug info by default** (found by the reporter). zig cc emits
  DWARF without `-g` (`-debug-info-kind=constructor` at `-O2`; `-g0`
  removes it), and rzig passes no `-g0`, although Makeconf's CFLAGS are
  `-O2` alone. linux keeps it in the installed `.so`: mlpack 304 MB on
  linux, 45.5 MB on macOS (DWARF stays in the `.o` files) and 31.1 MB on
  Windows (R links with `-s`); duckdb 426 MB, arrow 402 MB. Not a failure.
  Stock R's default flags are `-g -O2`, so a stock build is as large.

### R: rzig's own behaviour

- **R1. g++.exe's 8.3 name** (Windows). R starts programs by their short
  path, and g++.exe's is `G__~1.EXE` (`+` is not an 8.3 character). rzig
  names its tool from argv[0], so it prints its usage and exits 2. R CMD
  INSTALL's `g++ --version` fails in every C++ log (37 logs say `using C++
  compiler: 'NA'`). No install failed from it in this round: make starts
  g++ by its long name. Fix: name the tool from the long path (diff
  rzig-3, tested on kappa).
- **R2. The env's `-L` comes before the package's own `-L`** (a design
  point, as Makeconf's LDFLAGS had it). With tbb-devel in the env, `-ltbb`
  binds the env's TBB, not a package's bundled one. linux: the hand-built
  RcppParallel has `NEEDED libtbb.so.12` from the env (libstdc++), with the
  env first in RUNPATH, while its R code loads the bundled `libtbb.so.2`;
  it worked at smoke level and for Stan sampling. Windows: `-ltbb` binds
  conda's MSVC `tbb.lib` (undefined `tbb::detail::r1::*` in RcppParallel,
  stringfish, qs2 and rstan); naming the bundled TBB by path fixes it. On
  win-64 mkl also pulls in tbb.

### T: the tree's build (Windows)

- **T1. `R_ARCH` is empty in `etc/x64/Makeconf`** (CRAN R: `/x64`).
  winshlib.mk's `symbols.rds` step runs `$(R_HOME)/bin$(R_ARCH)/Rterm.exe`
  (igraph and duckdb list it in `all:`): `bin/Rterm.exe: No such file or
  directory`. arrow's `-L.../lib$(R_ARCH)$(CRT)` misses the prebuilt
  `lib/x64-ucrt`. `COMPILED_BY` is empty too. Fix: one `replaceLine` in
  build.zig (diff build-zig-windows-r-arch); checked only through a
  Makevars.user with `R_ARCH=/x64`.
- **T2. No `bin/R.exe` and `bin/Rscript.exe`.** The tree's `R_HOME/bin`
  holds `config.sh`, `toolchain` and `x64`; CRAN R also has the Rfe front
  ends there. Rmpfr's configure runs `${R_HOME}/bin/R CMD config CC` (then
  `no acceptable C compiler`); rstan's Makevars.win runs
  `${R_HOME}/bin/Rscript` for `STANHEADERS_SRC` and
  `RcppParallel::CxxFlags()`; s2's bundled-abseil path runs it too. Fix: a
  build.zig change (build Rfe). No diff.
- **T3. CMake on Windows.** `R CMD config CC/CXX` give
  `.../bin/toolchain/gcc` and `g++` without `.exe`, and CMake 4.4 stops: `is
  not a full path to an existing compiler tool` (RcppParallel; Rhdf5lib
  through biocmake). conda-forge's cmake picks `NMake Makefiles` when no
  generator is set (`make: invalid option -- ?`). `windres` is not on PATH
  for TBB's `.rc` file, and it needs `--preprocessor=<toolchain>/gcc.exe`.
  Tested with `.exe` compilers, `CMAKE_GENERATOR='MSYS Makefiles'`, `RC`
  and `RCFLAGS`. Where to set these is open (Makeconf, Renviron, rzig, the
  env).

### A: C++ ABI mismatch

- **A1. linux: conda-forge's C++ libraries use libstdc++**, the packages
  zig's static libc++. Six rows: magick (Magick++ 7.1.2:
  `magickImage(std::__1::basic_string const&)` against the exported
  `std::__cxx11` one), sf (`OGRGeometryFactory::forceTo(std::__1::unique_ptr)`
  against `St10unique_ptr`), terra (`GDALWarpOperation::Initialize(...,
  std::__1::unique_ptr)`), gdalraster (`_Z14CPLGetPathSafePKc` against
  `_Z14CPLGetPathSafeB5cxx11PKc`: libstdc++'s abi tag), protolite
  (`ArenaStringPtr::Set(std::__1::basic_string_view)`), and V8 at link time
  (the downloaded static `libv8_monolith.a`, v8-rocky-8-amd64, is
  libstdc++). Checked with `nm -D` on the env's libraries. lwgeom, the
  C-only control case, cannot be tested on linux while sf fails.
- **A2. Windows: conda-forge's C++ libraries are MSVC builds.** Their C
  APIs work: openssl, libxml2, udunits2, gmp, mpfr, nlopt, freetype,
  harfbuzz and fribidi. Their C++ APIs do not: terra 139 undefined
  symbols, gdalraster 31, protolite 71, s2 against `abseil_dll`
  (`absl::lts_20260526::*`). Before the link, the `.pc` files are
  MSVC-only: `gdal.pc` gives `-LIBPATH:` and a `Windows Kits` path (a shell
  syntax error in the link line); `absl_*.pc` give `/W3 /bigobj`. arrow's
  own Windows libarrow is gcc 10.3 and libstdc++: 403 undefined
  `std::__1` symbols once T1 is fixed.
- **No mismatch on macOS.** conda-forge's macOS libraries use libc++, the
  ABI of zig's libc++: sf, terra, gdalraster, protolite, s2 with the env's
  abseil, RcppParallel:system-tbb, magick and V8 all pass. Not tested: a
  C++ exception thrown in a conda library and caught in package code, with
  two libc++abi copies in one process.
- **Windows bundles built with clang pass.** The tree's R reports
  `R_COMPILED_BY` clang 21.1.8, so the winlibs.R scripts of magick, V8,
  curl and gert download the clang-x86_64 r-windows bundles, built against
  libc++. magick and V8 load and pass their smoke calls (the brief expected
  an ABI failure).

### S: missing system dependency (Windows)

- **S1.** conda-forge's win-64 glpk 5.0 has no `glpk.pc`, so igraph's
  `pkg-config --cflags libxml-2.0 glpk` returns nothing (`libxml/globals.h`
  not found). RPostgres expects Rtools' boost headers (`boost/shared_ptr.hpp`
  not found); with BH's headers, `-lpq` then finds conda's `libpq.a`, a
  static MSVC archive that asks for `libMSVCRT.a`. With `libpq.lib` by path
  plus `-lws2_32 -lsecur32` it installs and runs.

### U: upstream packaging

- **U1. macOS: conda-forge's libheif 1.23.4 to 1.23.6 for osx-arm64**
  (`gpl_hea44f65`) links `/opt/homebrew/opt/webp/lib/libsharpyuv.0.dylib`.
  magick's load test fails with `Library not loaded`, and so does the
  env's own `magick` program. 1.23.3 and the osx-64 build are clean (the
  omicron runner checked the packages). With
  `R_LD_LIBRARY_PATH=<R_HOME>/lib:<env>/lib` magick passes, so Magick++
  works across the boundary.
- **U2. Windows: `netcdf.pc`'s `Libs.private`** holds `-ldebug -lzstd
  -loptimized -lzstd` (CMake keywords). pkg-config on Windows adds
  `Libs.private`, so ncdf4's link asks for a library named `debug`.
- **U3. Windows: `gslcblas.lib`** is the import library of MKL's
  `libcblas.dll`, but it also lists `vfprintf`, `fprintf` and
  `_vfprintf_l`, which the DLL does not export. gsl.dll then imports
  `vfprintf` from it and `LoadLibrary` fails (`The specified procedure could
  not be found`). Linking without `-lgslcblas` works.
- **U4. conda: r-zig-slim build 4 (universe) needs `libdeflate >=1.26`,
  and every conda-forge libgdal-core needs `<1.26`.** A conda env cannot
  hold r-zig-slim with sf, terra, lwgeom or gdalraster (harness test,
  `logs/conda-env.log`). The tree is not affected (the lock holds 1.25).

### P: package-specific (Windows)

- **P1.** hdf5r's Makevars.ucrt hardcodes its `1_12_0` wrappers; conda's
  HDF5 2.2 has no `H5FD_family_init`. Not worked around.
- **P2.** s2's configure.win asks `pkg-config absl_base` (yes: conda's
  abseil), so it skips its bundled abseil; its `src/Makevars.win` asks
  `pkgconf`, which the env does not have, and links the bundled libraries
  that were never built. With conda's abseil forced, A2.
- **P3.** stringi's configure.win always uses its bundled ICU 74 on
  Windows. The package works; the row's smoke call (system ICU) is wrong
  for Windows.
- **P4.** Rhdf5lib's vendored HDF5 2.x turns `_Float16` on, but mingw-w64's
  `fenv.h` includes `<float.h>` before HDF5 defines
  `__STDC_WANT_IEC_60559_TYPES_EXT__`, and clang's `float.h` has one
  include guard around its `FLT16_*` macros: `FLT16_MAX` undeclared. With
  `-D__STDC_WANT_IEC_60559_TYPES_EXT__` it builds.
- **P5.** ragg's pkg-config branch does not link `ws2_32` (its rwinlib
  branch does): undefined `htons`. With `PKG_LIBS += -lws2_32` it passes.

### H: the harness

- **H1.** A target that installs and loads but fails its smoke call counts
  as failed, so its dependents are skipped: stringi's smoke call skipped
  textshaping and ragg on Windows. The merged classifier diff changes
  that (below).

## The classifier

There is no `upstream` class, so `sysdep` counts as its stand-in here (as
the runners' expectation diffs do). The runner's class then matched the
root cause for 5 of 12 failures on linux, 0 of 7 on macOS and 4 of 15 on
Windows. Each runner left a classifier diff; the three edit the same
lines. The reporter merged them (union of the patterns) into one diff,
which also carries the Windows runner's change for H1. On the run-1 logs
it classes linux 12 of 12, macOS 7 of 7 and Windows 12 of 15. The three
left on Windows: gsl (`package`), s2 (`sysdep`, not package) and arrow
(`sysdep`: the T1 layer is not visible in its log). With the merged
expectations these three rows would still show `(!)`.

The three expectation diffs edit the same rows too. The reporter merged
them field by field: each OS's own `expect` value, the notes in OS order,
and Windows' stringi smoke call. The merged file parses with stress.R
(`--sysdeps`), stays ASCII and has 10 fields on every row. Neither merged
diff is applied.

## What this tells feat-standalone-toolchain

**B39 (Windows `usr/bin`: sh, make, coreutils, sed, grep, gawk, which,
findutils).** The run cannot show that the list is enough. The win-64
stress env had all of it plus diffutils, tar, gzip, unzip, zip, patch,
texinfo, perl, less, a native make, pkg-config, MinGW binutils and cmake.
Every configure.win and Makevars ran under the env's m2 bash and make.
"command not found" appeared only for `windres` (CMake, T3). The other
missing programs were R's own: `bin/R`, `bin/Rscript` (T2) and
`bin/Rterm.exe` through `R_ARCH` (T1). A test of the list itself needs a
run with only B39's tools on PATH.

**B43 pkg-config.** Needed when there is a libraries env, and it must be
on PATH: packages do not use Makeconf.win's `PKG_CONFIG` line.
- igraph, hdf5r, ncdf4, sf, terra and gdalraster pick their Windows
  Makevars branch by whether `pkg-config --version` runs; s2's configure.win asks
  `pkg-config absl_base` and `pkg-config openssl`.
- systemfonts, textshaping, ragg and RPostgres write `PKG_CONFIG ?=
  $(BINPREF)pkg-config` and expand it with `:=`. R reads a package's
  Makevars before Makeconf (tools/R/install.R), so `BINPREF` is still
  empty there and the call is `pkg-config` from PATH. The logs agree:
  systemfonts printed `using freetype2 from Rtools`, which needs that call
  to return libraries, while Makeconf.win's `PKG_CONFIG` names
  `bin/toolchain/pkg-config`, a file that does not exist.
- s2's `src/Makevars.win` calls `pkgconf` by that name. pkg-config alone
  does not serve it.
- A pkg-config on PATH changes how these packages build. With the stress
  env's `.pc` files it led to the env's C libraries (good) and to conda's
  MSVC-syntax `.pc` files (A2, U2). What the pkg-config branches do with
  no `.pc` files at all (a standalone user without a libraries env) was
  not tested.

**B43 objdump.** No install used it. R CMD check's compiled-code check on
Windows does (`R CMD config OBJDUMP`, which must name an existing `.exe`,
else `objdump.exe` on PATH, else a warning; tools/R/sotools.R). The suite
does not run R CMD check, so it shows no need either way.

**B43 gcc-nm (and gcc-ar, gcc-ranlib).** No package used LTO and no log
calls them. No need shown: B43-2's "none now" holds.

**Other tools seen** (for B24 and the extras):
- nm: winshlib.mk runs `$(NM)` for every DLL without a `<pkg>-win.def`
  (the call is not echoed in the logs). igraph's and duckdb's
  `symbols.rds` step also runs `nm` from PATH (`Sys.which("nm")`; a
  warning when missing).
- windres: CMake looks for it on PATH (or `RC`), not through Makeconf's
  `RESCOMP`. With `binutils/` off PATH, CMake projects with `.rc` files
  need `RC` set, windres on PATH, or rzig serving it (B24's zig rc).
- ar and ranlib: 189 and 84 log lines use Makeconf's ar and ranlib

- B43's new rzig names `zig-ranlib.exe` and `gcc-ranlib.exe` are longer
  than 8.3. R would start them as `ZIG-RA~1.EXE` and `GCC-RA~1.EXE`, which
  rzig does not know (R1). The R1 fix (the long path) covers every name.
- CMake needs an existing compiler file (T3). B26 (a) drops the
